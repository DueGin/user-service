# Admin Boundary Requirements

## Summary

后台管理边界需要收束为两层：平台管理员管理统一账号体系和应用接入配置，应用管理员管理自己负责应用内的成员关系。每个应用从已有统一账号中指定一个或多个管理员账号；同一个账号可以负责多个应用，但必须在明确的应用上下文里操作。应用内用户管理不作为平台管理员的默认后台模块，也不能只靠隐藏导航来隔离权限。

---

## Problem Frame

这个用户中心服务的是自有产品生态。多个产品需要统一登录、统一账号体系和单点登录能力，避免每个系统重复做登录注册、账号割裂、接入慢、用户反复登录和权限边界混乱。

后台边界如果不清晰，平台管理员会同时看到平台配置和业务应用用户运营，应用负责人也可能被误授予全局用户或应用配置权限。当前需求要把“账号体系管理”和“应用内用户管理”分开，让团队成员负责自己的应用时不变成平台管理员。

---

## Key Decisions

- **应用管理员来自已有统一账号。** 创建或编辑应用时选择一个或多个已有且可用的统一账号作为应用管理员，不在应用创建流程里顺手创建新账号。
- **每个应用可以有多个管理员账号。** 当前产品语义是每个应用至少设置一个管理员账号；同一个统一账号可以负责多个应用，同一个应用也可以由一组团队成员共同管理。
- **平台管理员不默认管理应用内用户。** 平台管理员后台聚焦账号体系、应用接入配置、密钥、回调地址、应用管理员账号和审计排查；日常应用成员运营不进入平台管理员默认视角。
- **应用管理员只管理自己的应用成员关系。** 应用管理员管理的是“已有统一账号加入某个应用”的成员关系，不能创建全局账号，也不能管理全局用户、全局角色、应用密钥或其他应用。
- **权限边界必须落到服务端。** 导航隐藏只是体验层；页面路由和 API 都必须按当前身份和应用上下文做授权判断。
- **SSO 保持快速接入。** 首次授权可以自动沉淀应用成员关系，但不能绕过应用级禁用状态。
- **应用访问模式由应用配置决定。** `OPEN` 允许任意统一账号登录并自动沉淀成员；`MEMBERS_ONLY` 只允许已有活跃应用成员登录；`ADMINS_ONLY` 只允许该应用管理员登录。

---

## Actors

- A1. 平台管理员：维护统一账号体系和应用接入配置的人。
- A2. 应用管理员：团队里负责某个接入系统的人，账号来自统一账号体系。
- A3. 应用用户：使用统一账号登录一个或多个接入应用的人。

---

## Requirements

**平台后台边界**

- R1. 平台管理员登录后台后，不应默认看到应用内用户管理入口。
- R2. 平台管理员应能创建、编辑和禁用接入应用。
- R3. 平台管理员创建或启用可接入应用时，必须为该应用指定至少一个已有且可用的统一账号作为应用管理员；未指定时应阻止保存为可接入状态。
- R4. 平台管理员应能重新指派一组应用管理员；全部管理员账号被禁用、删除或失效时，该应用的应用管理员能力应被冻结，直到平台管理员重新指派。
- R5. 平台管理员应能查看审计日志并排查登录、授权和应用接入问题，但默认不直接进入应用成员列表做日常运营。
- R6. 平台管理员默认不能通过直接 URL 或 API 调用访问应用用户管理能力；排查路径以审计日志、账号状态和应用接入配置为主。

**应用管理员边界**

- R7. 被指定为应用管理员的账号应能登录当前后台。
- R8. 应用管理员登录后台后，只应看到自己负责应用的应用用户管理入口。
- R9. 同一个账号负责多个应用时，后台必须提供明确的应用选择或切换上下文；用户列表、启用、禁用和新增成员操作都必须按当前应用过滤。
- R10. 应用管理员只能查看、关联、启用或禁用自己负责应用下的应用成员；“关联”表示从已有统一账号中选择成员，不表示创建全局账号。
- R11. 应用管理员不能管理全局用户、全局角色、应用密钥、回调地址或其他应用。
- R12. 同一账号既是平台管理员又是某些应用的应用管理员时，默认进入平台管理员视角；应用用户管理必须通过明确的应用管理员上下文进入，不能把两类权限静默合并到同一导航里。

**应用用户边界**

- R13. 应用内禁用用户只影响该用户访问当前应用，不影响统一账号本身。
- R14. 同一个统一账号可以作为多个应用的用户，且各应用的启用状态彼此独立。
- R15. `OPEN` 应用中，用户首次通过第三方应用登录或授权时，如果该账号没有当前应用成员关系，系统应自动创建 ACTIVE 成员关系，以支持生态内快速接入。
- R15a. `MEMBERS_ONLY` 应用只允许已有 ACTIVE 成员登录；`ADMINS_ONLY` 应用只允许应用管理员登录。
- R16. 如果该账号已经被当前应用禁用，后续登录或授权不得自动重新启用，应拒绝当前应用访问，直到应用管理员手动启用。
- R17. 重复登录或授权不应创建重复成员关系，也不应绕过禁用状态；只更新必要的登录或授权记录。

**审计与反馈**

- R18. 应审计应用创建、编辑、禁用、管理员指派、管理员重指派、应用成员关联、启用、禁用、跨应用越权拒绝、密钥和回调地址变更。
- R19. 审计事件至少应包含操作者、目标应用、目标账号、动作、时间、结果和失败原因。
- R20. 应用用户管理界面应覆盖空列表、重复关联、成功、失败、无权限、当前管理员无可管理应用等状态。

## Key Flows

- F1. 创建应用并指定管理员
  - **Trigger:** 平台管理员要接入一个新的团队内部系统。
  - **Actors:** A1, A2
  - **Steps:** 平台管理员创建应用，配置回调和来源，从已有且可用的统一账号中选择一个或多个应用管理员账号。没有管理员账号时，应用不能保存为可接入状态。
  - **Outcome:** 应用可用于 SSO 接入，指定账号获得该应用的应用用户管理入口。

- F2. 应用管理员管理应用用户
  - **Trigger:** 某个接入应用需要启用、创建或禁用本应用用户。
  - **Actors:** A2, A3
  - **Steps:** 应用管理员登录后台，进入应用用户管理；如果负责多个应用，先选择一个应用上下文，再从已有统一账号中关联成员或调整成员状态。
  - **Outcome:** 应用用户状态变化只影响该应用。

- F3. 平台管理员排查接入问题
  - **Trigger:** 某个应用登录、授权或 token 交换出现问题。
  - **Actors:** A1
  - **Steps:** 平台管理员查看应用配置和审计日志，定位回调、密钥、来源或账号状态问题。
  - **Outcome:** 平台管理员排查身份基础设施问题，不承担应用日常用户运营。

- F4. 用户首次通过接入应用授权
  - **Trigger:** 用户使用统一账号访问某个已接入应用。
  - **Actors:** A3
  - **Steps:** 授权流程识别应用和统一账号；如果不存在成员关系，则创建该应用下的 ACTIVE 成员关系；如果已存在 DISABLED 成员关系，则拒绝当前应用访问。
  - **Outcome:** 新用户可以低摩擦进入自有生态应用，被应用禁用的用户不能通过重新授权绕过限制。

- F5. 平台管理员恢复失效应用管理员
  - **Trigger:** 某个应用的管理员账号被禁用、删除或不再可用。
  - **Actors:** A1, A2
  - **Steps:** 系统冻结该应用的应用管理员能力并提示平台管理员重新指派；平台管理员从已有可用统一账号中选择新的应用管理员。
  - **Outcome:** 应用管理权可以恢复，且不会自动落到平台管理员或无关账号上。

## Acceptance Examples

- AE1. Given 一个平台管理员登录后台，When 侧边栏渲染，Then 不展示应用内用户管理入口。
- AE2. Given 一个平台管理员直接请求应用用户管理页面或 API，When 该账号没有当前应用管理员上下文，Then 系统拒绝访问。
- AE3. Given 一个应用已指定管理员账号，When 该账号登录后台，Then 展示该应用的应用用户管理入口。
- AE4. Given 一个账号负责多个应用，When 进入应用用户管理，Then 必须先选择或明确当前应用，且列表只展示当前应用成员。
- AE5. Given 应用管理员尝试访问其他应用的用户列表，When 请求发起，Then 系统拒绝访问并记录审计事件。
- AE6. Given 应用管理员关联应用用户，When 输入一个已有统一账号，Then 系统为当前应用创建或更新成员关系，而不是创建新的全局账号。
- AE7. Given 应用管理员禁用某个应用用户，When 该用户访问其他应用，Then 其他应用访问不受该禁用影响。
- AE8. Given 平台管理员创建可接入应用，When 没有选择管理员账号，Then 系统阻止保存为可接入状态并提示必须选择管理员。
- AE9. Given 用户首次通过某应用授权，When 该用户没有该应用成员关系，Then 系统创建 ACTIVE 成员关系。
- AE10. Given 用户已被某应用禁用，When 该用户再次通过该应用授权，Then 系统拒绝访问且不自动重新启用。
- AE11. Given 同一账号既是平台管理员又是某应用管理员，When 登录后台，Then 默认展示平台管理视角；只有显式进入该应用上下文时才展示应用用户管理。

## Scope Boundaries

- 暂不做复杂 IAM、细粒度权限策略、应用内多角色或组织/租户体系。
- 暂不支持创建应用时同步创建管理员账号。
- 支持单应用多个管理员，但不引入更细粒度的应用内角色体系。
- 暂不把平台管理员设计成每个应用的默认应用管理员，也不把平台管理员 API 权限等同于应用管理员权限。
- 暂不把应用用户管理放进平台管理员的默认后台导航。
- 暂不做平台管理员的“破窗式”应用成员查看能力；如果未来需要，应单独设计只读诊断、强审计和访问理由。

---

## Success Criteria

- 新接入应用能在统一账号体系里选择一个或多个已有且可用账号作为应用管理员，未选择时不能启用为可接入应用。
- 平台管理员和应用管理员登录后台后看到的管理入口不同。
- 应用管理员无法越权管理其他应用或平台级配置。
- 应用用户状态可以按应用隔离，不破坏统一账号复用。
- SSO 首次授权能自动沉淀应用成员关系，且不会绕过应用级禁用。
- 管理员指派、成员状态变更和越权拒绝有可追踪审计记录。
